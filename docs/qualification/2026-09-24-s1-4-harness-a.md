## 2. Evidence checker rules

`s1_evidence.py check <record>` verifies against this checkout by default. A PASS or a closure without a repository to verify against is refused. The rules below are the ones a schema cannot express. The unit tests hold a negative test for each rule, and mutation testing shows each rule is load-bearing.

**Measured code**
- Every PASS unit's measured SHA must be a commit in the repository and reachable from `main` (plan §2). An unknown SHA is `measured_sha_unknown`; an unmerged one is `measured_sha_not_on_main`.
- Committed inputs the checker reads (the worker settings for the B3 timeout, the accepted B1 baseline) are read at the measured SHA with `git show`, never from the current checkout.

**Runs and provenance**
- Every run a unit cites has the unit's measured SHA and concluded `success`. A unit may only be measured on the record's `measuredSha` or the closure `mergeSha`, the two ends of the verified diff.
- Every suite result comes from a workflow run, never a local one (plan §3). A variant-bound or `task10:` result comes from the Task-10 matrix, whose committed invocation at the measured SHA fixes what ran. A .NET or web result comes from the Quality Gate.
- Each `task10:<step>` result is backed by Task 10's own `junit/<step>.xml`. Each .NET suite is backed by the Quality Gate's `trx/<Project>.trx`, and the web suite by `junit/mavi-web.xml`.

**Suite results**
- Counts and test names are recomputed from the retained, hash-verified JUnit XML or TRX. That file must come from the cited run. In a TRX, each result is joined to its test definition for the class name; outcomes other than `Passed` and `NotExecuted` (an xUnit skip) count as failures or errors. xUnit truncates long theory arguments (`···`), so distinct cases can share a display name. A shared name carries each case's own TRX `testId` (`Name(…) [testId=…]`, a stable hash of the full case), so every execution stays a distinct, unique name: none is merged, dropped or invented, and a name that is not shared keeps its exact form. A case maps to its test function by the leading identifier of its member name, so pytest `[params]` and xUnit theory `(args)` both resolve to the function; a proving test is proven only when every one of its cases passed (none skipped, and no failed or errored case in the suite result). See `docs/qualification/stage2-s1/2026-09-26-m2-checker-case-identity-decision.md`. A committed, pruned capture of real SDK 10.0.112 TRX output holds the parser to the real format. Suite membership is derived from the suite path, on component boundaries.
- A variant-bound JUnit artifact declares its variant and names it as the XML test-suite name (Task 10 passes `-o junit_suite_name=<variant>`). Its bytes are not reused under another variant.
- A skip is admitted only if it is on the §3.1 list:
  - the POSIX lifecycle case and the 12 POSIX `test_artifact_store.py` cases, on Windows;
  - the 18 `test_artifact_store_windows.py` cases, on Linux;
  - PR A's own platform-specific memory-probe tests, each on the other OS.
- In a whole-step Task-10 file (`task10:s1-boundary`, `task10:s1-qualification-harness`), each skip is approved against the source suite its class name belongs to, not the step.
- A test pins that list to the OS-conditional tests of every required worker suite, including methods of test classes and class-level `skipif`. The golden-byte test is not on it.
- An approved skip still needs the same test of the same suite to pass on the other variant, in a result the same unit cites, from a successful run on the measured SHA.
- A suite whose every test is an approved skip (the Windows store suite on Linux) is not "empty". Any other suite that passed nothing is.

**Measurements**
- One value per metric; a second, failing value cannot hide behind a passing one.
- Every value cites a retained artifact of its own unit.
- The plan's limit binds whatever the record declares.
- **B1:** the four counts must equal those of the retained `s1-b1-comparison-v1` output, which must have been derived on the clean measured SHA with no identity problem. Its Linux input must be the retained `b1.real-clip-measurement`, its baseline the committed baseline at the measured SHA, and every trace must name a path, cause and reviewer.
- **B2**, for each of `linux-x86_64-cpu` and `windows-x86_64-cpu` separately (metrics are named `<metric>.<variant>`): the values must equal that variant's retained `derive` output. That output must:
  - have run on that variant, on the measured SHA, from a clean tree;
  - match the cited host on every measured field (CPU model, physical and logical cores, RAM, OS, OS build, staging filesystem);
  - carry at least five stepped live levels whose recomputed fit is the recorded per-live-Track slope, with its fit quality, and a bound-1 reconciliation consistent with that slope;
  - define both ±10 % variations. An undefined variation (a non-positive baseline, or one too noisy to resolve 10 %) is `variation_undefined`, and B2 cannot pass from it;
  - keep the staging peak within the run's derived bound (ratio ≤ 1.0).
- **B2 staging lifecycle:** each variant's `s1-b2-staging-lifecycle-v1` output, on the clean measured SHA and native ByteTrack, with every lifecycle check holding.
- **B3:** the worker timeout must be the `WorkerSettings` default at the measured SHA. B3 needs a sealing wall time for each supported Development OS (§7.4). Each must cite that OS's authoritative sealing output, measured on the B3 SHA from a clean tree, on the host's declared evidence filesystem and CPU (model, logical cores). Its stats, counts and timeout must equal the record's. Each body-size value needs its proving test to have passed in the cited suite (see §6).
- **B5:** the clip count must equal the retained real-video record's clips that are labelled `real-video`, have distinct SHA-256s and verified completion, Track detail and Evidence Set, on the measured code. The visual-QA record must pass every item and include a real-video item.

**B6 and disconnected evidence**
- **B6** needs every Task-10 JUnit step on both variants. It also needs each variant's six Task-10 JSON records from that variant's Task-10 run, at `<variant>/<record>`. The ByteTrack and production-composition records must name the measured head (and ByteTrack the variant) and must not be the other variant's bytes.
- **The disconnected unit** runs on a qualified CPU variant, on a host of that variant's OS. It needs:
  - the retained Runtime Bundle manifest (`sourceCommit`, `platformVariant`, a single `mavi-vision` wheel hash);
  - the before and after isolation probes as retained probe output, whose probe fields equal the record's, probing exactly the five targets of the reused `assert_outbound_internet_unavailable`;
  - an `s1-disconnected-run-v1` run record on the measured code, with every §11 outcome passed and no outbound connection attempts. Each outcome must be backed by its own retained evidence from the same local run as the run record, and no other unit may cite that evidence.

**Closure (§2.3, §10.4)**
- The merge SHA must be a later commit, descending from the measured SHA and on `main`.
- `changedPaths` must equal `git diff --no-renames --name-only`. Without `--no-renames`, a moved file would show only its new path.
- A change to a cited suite, or to shared test support in its project (conftest, fixtures, any file of a .NET test project), invalidates the citing unit. A `task10:` step covers every test file the workflow step runs; a test holds that table equal to the workflow. A change under `tests/fixtures/` invalidates every unit resting on any suite. So does a change to the sealing harness or `QualificationGate.cs`, cited or not.
- This is stricter than plan §2.1's wording, which counts only cited tests. It is deliberate: helpers such as `ApiTestFactory` change what cited suites test without being cited themselves.
- `s1Closed` needs successful Quality Gate, Task 10 and Task 17 runs on the merge SHA.

**Residual trust.** The checker verifies that retained bytes match their recorded hashes and their content. It cannot verify offline that a file was downloaded from the GitHub run it names. PR B's retention step should record each file's workflow-artifact name and digest from the GitHub API when it downloads the file.

## 3. B2 declared workload (plan §6.2, "declared up front")

**Frame source:** `synthetic-noise-pool-v1`. A deterministic pool of eight seeded uniform-noise RGB frames is cycled through the `VideoProcessor(frame_reader=...)` seam. The declared source file is still opened and SHA-verified; only decoding is substituted. Lossless and high-entropy, so crops keep their size.

**Scene:** `L` fixed grid slots. Each slot shows one subject for `track_frames` frames. The box grows by 35 % over its lifetime, so near-view, early- and late-diverse roles occur. The slot then stays empty for 45 frames (1,500 ms), longer than the 1,033 ms ByteTrack retirement horizon at `lostTrackBufferSeconds = 1.0`, so the subject is retired before the next one appears. Slot phases are staggered.

The wall-time estimates assume about 1 ms per live observation on a Linux development container. They are a budget, not a measurement. Every output records its actual `processingSeconds`.

| Preset | Mode | L | Retirements | Track frames | Box px | Frames (approx.) | Budget |
|---|---|---|---|---|---|---|---|
| `b2-retained-baseline` | tracemalloc | 16 | 1,000 | 450 | 144 | 31,000 | ≈ 8 min |
| `b2-retained-long` (10×, > 4,096-point chunk) | tracemalloc | 16 | 1,000 | 4,500 | 144 | 284,000 | ≈ 75 min |
| `b2-retained-large-crops` | tracemalloc | 12 | 1,000 | 450 | 224 | 41,000 | ≈ 8 min |
| `b2-process-memory` | process, tracemalloc off | 32 | 5,000 | 90 | 128 | 21,000 | ≈ 12 min |
| `b2-completion-peak` (≤ 10,000 Tracks) | tracemalloc | 64 | 9,936 | 30 | 96 | 11,800 | ≈ 6 min |
| `b2-live-{4,8,16,32,64}` | process, tracemalloc off | 4–64 | 400 | 150 | 96 | ≤ 19,500 | ≈ 3 min each |

Every authoritative preset uses the native ByteTrack adapter. `FixtureTracker` appears only in the structural tests (§6.2: it cannot see native backend state).

Each preset runs in its own process, on each qualified CPU variant:

```
python tools/qualification/s1_memory.py run --preset <name> --output <dir>/<name>.json [--work-root <qualified filesystem>]
python tools/qualification/s1_memory.py derive <dir>/*.json --output <dir>/b2-derived.json
```

`derive` refuses an output when:

- it did not use ByteTrack;
- it fell short of its declared retirements;
- its source SHA is unknown, or its tree is dirty;
- it did not run on a qualified runtime variant;
- its workload is not exactly its declared preset;
- its source, runtime or host identity differs from the other outputs'.

It emits exactly the base metric names `s1_evidence.B2_BASE_MEASUREMENTS` lists; the record names each per variant (`<metric>.<variant>`), from one derive output per qualified CPU variant. Among them:

- **Bound 1 trajectory term:** buffered points ≤ one 4,096-point spool chunk.
- **Variation (bound 2):** the plain relative change of the slope, with no denominator floor (plan §6.2). When the baseline slope is not positive, or its standard error is at least 10 % of it, the variation is emitted as undefined with its reason; the checker reports `variation_undefined`.
- **Per-live-Track slope:** process memory against the five stepped live levels, emitted with the plateau points, `n`, fit and r². It is a mandatory metric with no limit. `boundOneReconciliation` puts it beside the largest encoded bytes and trajectory points a live Track was accounted as holding and the 544 KiB encoded-holder bound, and reports the unaccounted remainder. 544 KiB bounds held encoded evidence, not process memory, so the slope is reconciled with it, not thresholded, and is the regression baseline (plan §6.2 as amended).
- **Staging:** each run's staging root is its real `media/staging/<job>/attempt-NNNN` directory. The run reports its peak and its derived bound, Σ over its Tracks of 544 KiB plus the trajectory artifact bytes and spooled observation records (plan §6.3). `b2.staging-peak-to-derived-bound-ratio` must be ≤ 1.0.

The harness asserts no PASS; the checker applies the limits.

**Staging lifecycle (plan §6.3).** A separate command runs the lifecycle through the real staging store and native ByteTrack:

```
python tools/qualification/s1_memory.py staging-lifecycle --output <dir>/b2-staging-lifecycle.json [--work-root <qualified filesystem>]
```

It runs four attempts in sequence:

1. a failed attempt, which must clean its own staging;
2. an attempt that loses its lease, whose staging must be retained;
3. a sibling job, which the others must never touch;
4. a superseding attempt, which removes the superseded attempt's directory and keeps its own successful staging for the platform janitor.

Every phase's peak must stay within its derived bound.

**Process metrics.** On Linux the harness reads USS (Private_Clean + Private_Dirty), PSS and RSS from `/proc/self/smaps_rollup`, and the peak from `VmHWM`. On Windows it reads `PrivateUsage` through `GetProcessMemoryInfo` via `ctypes`, and names it **commit charge**, not USS. `psutil` is not used.

## 4. B4 commit-boundary semantics exercised

These are the store's real semantics, not a stronger claim:

| Injected fault | Database | Newly sealed evidence | Log | Replay |
|---|---|---|---|---|
| Fails before commit; rollback confirmed | nothing committed | **compensated** (deleted) | — | a retry completes normally |
| Commit succeeds, then the call fails | **committed** | retained (rollback cannot be confirmed) | event 1301 | exact replay is idempotent: same run, no duplicate rows |
| Fails before commit; rollback fails | nothing committed | **retained, unreferenced** (no Artifact row, so not addressable) | event 1301 | exact replay adopts the same files in place |
| Process loss after sealing, before commit | nothing committed | sealed, unreferenced | — | exact replay adopts them; a second replay is idempotent |

Retained, unreferenced evidence after an ambiguous outcome is intended. Deleting it could orphan committed rows.

## 5. B3 sealing harness (engineering observation only)

`S1SealingScaleTests.RealStoreCompletionWallTimeAtTheWorstCaseObjectCount` is skipped unless `MAVI_QUALIFICATION=1`. It measures a complete completion 3.0 POST at 10,000 Tracks with four crops each: 50,000 sealed objects through the real accepted-evidence store, on the filesystem of `MAVI_S1_SEALING_EVIDENCE_ROOT`. Each sample is followed by a timed exact replay. The output records n, min/p50/p95/max, the p50 spread across repeats, the filesystem, the row counts and the worker request timeout the checker compares against (2× headroom). The defaults are 30 samples × 3 repeats after one warm-up.

The worker timeout is the worker's own `MAVI_REQUEST_TIMEOUT_SECONDS`, defaulting to the 30 s `WorkerSettings` value, not a harness knob. The output is marked `authoritative: false`, with its reasons listed, when any of these holds:

- the envelope is reduced below 10,000 Tracks, 30 samples, 3 repeats or 1 warm-up;
- the timeout is overridden;
- PostgreSQL is not 18;
- the tree is not clean;
- the host is not a qualified x86-64 Linux or Windows variant.

The output also records its runtime variant and host (CPU model, logical cores). The checker needs one authoritative sealing output per supported Development OS and binds each to the record and its host (§2). The harness creates and deletes its own `mavi-s1-sealing-<run>` directory under `MAVI_S1_SEALING_EVIDENCE_ROOT`; nothing else there is touched.

The timeout must equal the 30 s `WorkerSettings` default. No supported install path configures `MAVI_REQUEST_TIMEOUT_SECONDS`, so a non-default value needs a checker change that parses a real install configuration; a cited file is not enough.

**Engineering observation, not evidence.** This is a single smoke sample (n = 1, no warm-up, no repeats), taken while the harness was developed. The host was a shared development container: ext4 at `/`, PostgreSQL 18.6, uncommitted tree. It is not a qualified host.

- One 10,000-Track, 50,000-object completion took **≈ 94 s** end to end. The exact replay took ≈ 0.9 s.
- That is about 3× *over* the default 30 s worker request timeout. B3 needs ≤ 15 s.
- The harness persisted exactly 10,000 Tracks, 40,000 Observations, 50,000 Artifact rows and 50,000 accepted files.

If a qualified host reproduces this, B3 fails on §7.4 as written. The cost is per-object durable publication (file flush plus directory-chain fsync) inside the `FOR UPDATE` transaction. That is a product or plan decision for PR B, not for this tooling PR. Nothing here changes sealing, the timeout or the plan's bound.

## 6. Trust boundary and runbook notes for PR B

**Content binding.** What the checker compares, and what it trusts by provenance alone (a retained, hash-verified file from a verified run):

- *Compared with retained content:*
  - B1 counts, recomputed from the comparison of retained runs against the committed baseline;
  - B2 values, the live-level fit, the reconciliation, the staging ratio and the lifecycle checks, per variant;
  - the B3 wall times, timeout and hosts;
  - the B5 clip count and visual QA;
  - the disconnected manifest, run record and probes;
  - the Task-10 ByteTrack and production-composition records;
  - every suite count, from JUnit or TRX.
- *Provenance plus a proving test:* the two B3 body sizes. Their values are not in any retained output. Each is admitted only when its proving test passed in the cited suite:
  - Python: `test_worst_shape_body_stays_within_the_budget` in `test_worker_completion_v3.py`;
  - .NET: `WorstShapeBodyFitsUnderLimit` in `WorkerContractV3Tests`.
  Those tests assert the 40 MiB and 32 MiB budgets themselves, so a passed test proves the value is within its limit. It does not prove the exact figure the record states.
- *Provenance only:* the Task-10 `runtime-probe.json`, `resolved-config.json`, `runtime.json` and `production-runtime-smoke.json`. Task 10's own steps validate their contents before the run can succeed, and B6 requires that run's success on the measured SHA. `runtime.json` is a copy of a committed file, so it can legitimately be identical on both variants.

**Suite completeness.** The checker does not diff a result's test cases against a `--collect-only` list. Completeness rests on the rule that a variant result must come from the Task-10 workflow on the measured SHA, whose committed invocation fixes what runs. Retaining collection output would close this, for a Task-10 step change in PR B.

**Write outputs outside the checkout.** Every harness output records whether the tree was clean, and the checker refuses one that was not. Write `--output`, `--work-root`, detection recordings, TRX/JUnit downloads and retained files outside the repository checkout. Anything written inside it makes the tree dirty and the output unusable.

**B1 procedure.** On each qualified variant, run `measure_evidence_real_clips.py` twice on the same clips; on Linux, add `--record-detections <dir>` to the first run. Replay the Linux recording with `--replay-detections <dir>`. Then derive the counts:

```
python tools/qualification/s1_b1.py compare --linux L1.json --linuxRepeat L2.json --windows W1.json --windowsRepeat W2.json --linuxReplay R.json [--traces traces.json] --output b1-comparison.json
```

Only host timing (`processingSeconds`, `peakRssKiB`) is excluded; every other difference is a count.

## 7. Non-claims
