**Status:** Authoritative current capability-development roadmap. This file controls *what MAVI builds next*. It does not control Production qualification (Task 18) and it does not restate or reinterpret historical evidence.

**Baseline:** `main@e38af446d4e287cb12a8cf3d881e0293f90f7d6d` (Scene Analytics Stage 1 / PR #70 merged and post-merge verified)

## 2. Sequencing decision — 20 September 2026

MAVI today understands recorded video, person/vehicle detections, Tracks, observations, trajectories, time, confidence and evidence playback. That is a sound base but semantically thin: a Track says little beyond *broad class, when, where in the frame, for how long, and with what confidence*.

Building an audited review and cases layer on top of that now would give operators a workflow for cataloguing detections rather than investigating intelligence. The decision is therefore to **increase what MAVI can understand and retrieve from video first**, and to build heavier investigation and reporting workflow **after** the underlying data justifies it. Deterministic capabilities that need no new model come before model-based ones, so each model-based step inherits searchable, explainable structure and a proven offline-qualification path.

The sequence:

| # | Capability | Kind | Why here |
|---|---|---|---|
| 1 | **Spatial & Temporal Track Analytics** | Deterministic; no new model | Largest intelligence gain from data already persisted; establishes scene configuration, derived-fact persistence and analytic search that every later stage reuses |
| 2 | Visual Attributes | Model-based (attribute classifier) | First appearance semantics; populates the existing `VisualAttribute` groundwork |
| 3 | Expanded operational object / vehicle classes | Qualification change, possibly detector change | Makes attribute and plate work class-aware |
| 4 | ANPR / OCR | Plate detector + OCR | Vehicle identity cue tied to Track evidence; pretrained candidates are benchmarked before any fine-tuning/training |
| 5 | Visual Similarity / query-by-example | Embedding model + pgvector | "Find similar" over persons and vehicles; results are similarity candidates, never identity assertions |
| 5A | **Face Intelligence** | Face detector + face embedding + pgvector | Query-by-face, previous appearances and candidate matching against an enrolled authorised-person gallery |
| 6 | Person/Vehicle ReID and candidate Entity association | Builds on 5; face is an additional person cue when 5A exists | Proposes candidate associations from multiple evidence cues; never silently merges Tracks |
| 7 | Event / Behaviour Analytics | Deterministic rules over 1, 2, 6 and time | Measurable events only, after their inputs exist |
| 8 | **Structured Intelligence Query + Aggregations** | API/UI | Composes predicates and deterministic operations such as find, count, distinct-count, group-by, time-bucket, first/last, top and bounded comparison |
| 9 | **Ask MAVI / Natural-Language Intelligence Query** | Small offline-capable language model translating to 8 | Gives ordinary operators a simple question interface; MAVI's deterministic query engine, never the language model, computes factual answers |
| 10 | Audited human review / cases | Identity, audit, workflow | When there is enough intelligence to investigate; design retained in the deferred plan |
| 11 | Live RTSP / VMS integration | Platform phase | After recorded-video intelligence is mature; see §6 |

Not next: live cameras; operator identity/audit as a major feature; cases or report generation. Identity/audit plumbing may still arrive earlier as a *small* enabler if a concrete operator mutation needs attribution — enrolment or maintenance of an authorised-person gallery is one such mutation — but it is not a roadmap stage.

### 2.1 Operator questions the sequence must ultimately answer

The roadmap is capability-first, but the end product is judged by operator questions rather than by model names. Representative questions that the planned stages must make answerable, with evidence behind every result, include:

- "How many **Person Tracks** crossed Main Gate Line between 0800 and 1400, and how many crossing events occurred?" Until Entity association exists, MAVI says *Person Tracks*, not "unique people".
- "How many vehicles crossed in each direction, by hour?"
- "Show vehicles whose plate contains `KA01`, with the plate crops and OCR observations."
- "Has this face appeared in the premises before? Show every candidate appearance and the cameras/times involved."
- "Is this face a candidate match to an enrolled authorised person? Show the reference and observed evidence."
- "When and where was this confirmed/candidate Entity last observed?"
- "Show the Tracks and evidence behind this answer."

The advanced structured Search surface remains the precise, reproducible evidence-query builder. Stage 9 adds a separate **Ask MAVI** surface for ordinary-language questions over the same deterministic query semantics; it does not replace or weaken Advanced Search.

## 4. What each future capability introduces

Every stage below that adds a model, Python library, native runtime, OCR engine, embedding model, npm or .NET package, database extension or OS prerequisite must, **in the same pull request**, update `config/dependencies/offline-dependency-policy-v1.json`, the offline packaging and setup path, verification, licences and runbooks (`docs/architecture/dependency-and-offline-packaging-policy.md`). Every model-based capability ships with a manifest, version, hash, runtime-compatibility statement, offline-pack location and its own qualification evidence, on the pattern the RTMDet Model Pack and Runtime Pack already follow (ADR-005, ADR-007). Nothing resolves online at install or first run.

**Model-family uniformity is not a product goal.** ADR-014 makes capability identity independent of model/vendor/framework identity, and the Model Selection Record method keeps technical ranking separate from licence/deployment assessment. MAVI may therefore use RTMDet for general detection, a YOLO-family or other specialist detector for plates, a separate OCR engine, specialist face models and another embedding model if measured capability performance supports those choices. Shared architecture is the capability binding, evidence/provenance, lifecycle, offline packaging and qualification contract — not a single neural-network family. Established pretrained models are evaluated first; fine-tuning or new training follows only from a demonstrated benchmark gap.

## 5. Architecture notes for later stages

These notes fix direction so later plans start from shared assumptions. They are not designs.

**Visual Attributes (stage 2).** Architecture-frozen plan: `2026-09-23-visual-attributes.md`, accepted ADR-013 and ADR-014. Raw multi-view Track evidence is selected inside VisionJob under explicit byte bounds; learned attributes run later in an independently leased/fenced process over lease-scoped hash-verified accepted evidence. Model/runtime binding is capability-oriented rather than detector-special-cased. Initial scope is person upper/lower clothing colour, bag/backpack, qualified headwear/helmet, and vehicle dominant colour. Vehicle subclass remains Stage 3 unless deliberately rebaselined. No attribute is exposed unless its frozen qualification gate is met.

**Person taxonomy (recorded 2026-10-06).** `Person` stays the stable base class, with `pedestrian` and `rider` as intended subtype/state concepts. A future BDD100K Person benchmark should evaluate BDD `pedestrian` and `rider` as candidate mappings to these subtype/states, but each dataset-native mapping must first be classified `exact`, `subset` or `unsupported` with its rationale under ADR-017 before measurement (BDD100K publishes no written class definitions; `docs/superpowers/plans/stage3-benchmark-capability-matrix.md`). Subtype/state never determines Person Track identity: the same person can move between pedestrian and rider within one Track. This records direction only; there is no Person subtype inference work, ADR-016's representation (Person Tracks carry no subclass) is unchanged until an ADR says otherwise, and H3 keeps its capability `mavi-vehicle-subclass-v1`.

**ANPR / OCR (stage 4).** Flow: `Vehicle Track → selected Track evidence → plate detection → plate crop as sealed derived evidence → OCR observations → searchable plate text`. Stage entry first measures whether the existing bounded Track Evidence Set preserves sufficient plate pixels; the VisionJob evidence contract changes only if that measurement demonstrates a real gap. Pretrained plate/OCR candidates are benchmarked as complete compositions before any fine-tuning or training. A Track may carry several OCR observations (different frames, different readings) each with detector/OCR confidence; raw text is immutable evidence, normalisation is a separate versioned derivation, and every hit links back to the crop and source frame.

**Visual Similarity (stage 5).** Embeddings per Track representative/supplemental crop(s) stored with model version and dimension; pgvector nearest-neighbour search; UI concept `Find Similar` from the inspector or Review page. Results are presented as **similarity candidates** with a score and evidence side-by-side, never as "same person" or "same vehicle".

**Face Intelligence (stage 5A).** Person Track evidence is analysed by a specialist face detector, quality/alignment step and face-embedding model. Persisted `FaceObservation`/embedding records retain source Track observation, face crop/geometry, model versions and quality/provenance. Query-by-face returns candidate Person Tracks across cameras/time. An operator-managed **enrolled authorised-person gallery** holds one or more reference images/embeddings per person; comparison against that gallery yields a *candidate known-person match* with score/evidence, never a silent hard identity assertion. A query image used only for search is transient unless deliberately enrolled. Gallery enrolment/update is a consequential identity mutation and therefore pulls forward the minimum attributable operator/audit plumbing needed even if Stage 10's full cases workflow remains deferred.

**ReID (stage 6).** Only after similarity retrieval is stable. `Track` remains one observed trajectory; `Entity` is a hypothesised persistent real-world subject across Tracks. Initial ReID proposes candidate associations for an operator to inspect. Vehicle candidates use appearance/time/camera evidence; Person candidates may additionally use Stage-5A face similarity where a usable face exists. Face is an independent cue, not a prerequisite and not a substitute for the rest of the evidence. `Track.EntityId` is written only by an explicit, attributable decision, which is why Stage 10's identity/audit work becomes relevant here.

**Event analytics (stage 7).** Combine zones, trajectories, dwell, attributes, Entity candidates and time into measurable events: intrusion, loitering, wrong-way movement, stopped vehicle, repeated visit, crowd build-up, group movement, co-occurrence. Each event is bound to its inputs and rule version and is explainable from evidence. No claim of intent or anomaly detection is made before the measurable events it would rest on exist.

**Structured Intelligence Query (stage 8).** Consolidate the predicates produced by prior stages and add a small typed aggregation algebra rather than arbitrary SQL: `find`, `count`, `countDistinct`, `groupBy`, `timeBucket`, `first`, `last`, `top` and bounded `compare`. Cardinality is explicit: event occurrences, Tracks and Entities are different answer units. Before Entity association, a query asking "how many people" is answered in truthful Track terms (for example, "45 Person Tracks produced 52 crossing events"), not silently converted into a unique-person claim. Advanced Search remains the precise operator/evidence query builder over this contract.

**Ask MAVI (stage 9).** A separate, simple operator surface accepts ordinary-language questions and translates them to the Stage-8 whitelisted query/function contract. The local language model **interprets; MAVI computes**. The deterministic query engine produces counts, rows, groups and time series; a deterministic/templated result renderer turns those outputs into concise factual answers, charts or tables with links to the underlying Tracks/events/evidence and a visible "Interpreted as" summary. Follow-up questions modify an explicit prior structured query. The model never runs unrestricted SQL, never invents an analytical count, never substitutes for face/plate/ReID models, and never bypasses Stage-8 validation.
## 6. Live cameras: a separate later platform phase

Nothing on any branch ingests live streams; import is file-based by design. Live ingestion is not "the import path, but continuous". It adds platform concerns that recorded-video work never touches and that each need design and qualification: RTSP and VMS integration; reconnect and stream-health semantics; buffering and backpressure; clock and time authority for live frames (ADR-004 extended); retention and rolling storage; continuous jobs rather than run-per-video; GPU scheduling across streams; load shedding; long-running recovery. This phase begins with its own ADR and after recorded-video intelligence (stages 1–8) is mature. Nothing from it is implemented now.

## 7. Roadmap versus Task 18 qualification

These are two different sequences and must not be collapsed:

- **Task 18 — Production Qualification and Phase-1 Closure** (`2026-09-18-task-18-phase1-production-qualification-rebaseline.md`) is a qualification and release stream. It may proceed independently of, and in parallel with, capability development.
- **This roadmap** decides which capability is developed next.

Consequences: a new Development capability does not become Production-qualified by being merged; PR #49's Development CUDA evidence does not equal P1 or P2 qualification; and a future feature must not silently invalidate existing qualification evidence. Where a feature changes a qualified artefact (runtime profile, component binding, model manifest, checkpoint, pipeline profile), the qualification records that bind those artefacts by digest are re-derived deliberately and the change is stated in the PR, exactly as PR #49 did for the runtime-profile digest.
