# PoC S1 — Deployable PoC v0: spike findings and design

**Status:** implementation record for slice S1 of `docs/superpowers/plans/2026-10-28-mavi-poc-end-to-end.md` (register rows A2–A5). Profile `poc-single-host` (ADR-020). Evidence class Development.
**Date:** 2026-10-28.

## 1. Spike: the existing bundle path on a clean target

Principle 10: before building, the existing path (`Setup-MAVI.ps1`, `New-MaviOfflineSetupBundle.ps1`, `New-MaviOfflineBinaryKit.ps1`, runbook "Production workstation", P3) was traced end to end against a clean, disconnected Windows target. Each hidden Development assumption below is a reason the existing path cannot install the PoC stack as it stands, and each names how S1 handles it.

| # | Hidden assumption | Where | S1 handling |
|---|---|---|---|
| H1 | The Vision worker launcher needs **`git.exe` and a repository checkout**: the application revision is `git rev-parse HEAD`, and the worker must import `mavi_vision` from `<repo>\src\vision` (an installed copy is refused as `launch_vision_source_overlay_foreign`). Setup's readiness check (`Start-MaviVisionWorker.ps1 -VerifyOnly`) needs git too. | `Start-MaviVisionWorker.ps1` (git probe, source-overlay lock); `Start-MaviPlatesPilotWorker.ps1` (git) | The PoC bundle carries an **application overlay**: a git-free export of the repository subset the workers read (`src\vision`, `config`, `contracts`, `models`, `tools`) in the repository layout, with `mavi-application-overlay.json` recording the exact commit and a SHA-256 for every file. ## 2. Design

**Bundle.** `tools/setup/New-MaviPocSetupBundle.ps1` assembles `MAVI-PoC-Setup\` from the verified Offline Binary Kit (PostgreSQL runtime pack, FFmpeg through the publish), the framework-dependent API+UI publish, the kit's Hosting Bundle, the application overlay, the Vision Runtime/Model Pack sources, the plates wheelhouse and payloads, and an optional smoke clip, then hashes every file into `mavi-poc-bundle.json` (`mavi-poc-setup-bundle-v1`).

**Install.** `Install-MAVI-PoC.cmd` → `Install-MAVI-PoC.ps1` (idempotent, `-PlanOnly`, no network): verify bundle → MAVI-owned PostgreSQL 18 + pgvector (`MAVI-PoC-PostgreSQL-18`, port 55434, DPAPI credentials as Production) → ASP.NET Core 10 runtime when absent → application and overlay → Vision CPU Runtime Pack → CUDA Runtime Pack when a compatible GPU (compute capability 7.5, the `sm_75` pack) is detected → bound Model Packs → plates runtime and its Model Packs → machine configuration → release metadata → launcher readiness check (`-VerifyOnly`, `Auto`) that records the resolved device and reason → start, seed the demo cameras, stop. Every step prints the disclosure.

**Device policy.** ADR-008 unchanged. `Auto` uses the CUDA pack only when installed, intact, bound and its GPU index answers; otherwise CPU, with the reason code. Explicit `CUDA` fails closed (`launch_runtime_pack_not_installed` when no CUDA pack is installed; the worker refuses a missing device at startup).

**Disclosure (ADR-020 §3).** Release metadata (`mavi-poc-release-metadata-v1`) carries profile, `productionQualified: false`, evidence class and pack identities. The API reads it through `Deployment:*` configuration; under `poc-single-host` the disclosure fields in the response are constants of the code, and startup refuses metadata that claims anything else. No configuration key hides them. The React shell renders a persistent, non-dismissible banner for the profile and a System page with the full disclosure.

**Not in S1.** Binding the plates role (S3); a shippable CUDA variant (S1b); demo media and scene geometry (S2); a Windows service host.
