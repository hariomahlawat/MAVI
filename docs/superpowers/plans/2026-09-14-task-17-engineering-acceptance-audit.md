# Task 17 — Engineering Acceptance Audit

**Scope:** implementation readiness of PR #38 against the accepted Task-17 plan and qualification-closure addendum.

**Important distinction:** this audit can conclude implementation-complete while release verification remains evidence-pending. CUDA, disconnected install/update, CCTV quality and Linux NVIDIA recovery/performance gates must never be inferred from connected CI.

## 1. Requirements completeness

Implemented acceptance contracts cover:

- deterministic ground-truth schema, corpus binding and evaluator;
- Person and Vehicle independent formal-quality policy;
- exact processed-media SHA-256/ETag/duration binding before scoring;
- completed-run attestation API with stable allowlist;
- public-API E2E harness with exact ProcessingRun/Track/Evidence bindings;
- application artifact identity plus fresh-install and offline-update qualification;
- all four Windows/Linux CPU/CUDA runtime variants;
- complete bundle hostCompatibility comparison;
- strict no-index/hash-only offline install and real inference;
- full worker-flow evidence requirement for each variant;
- Linux NVIDIA recovery/performance evidence evaluated against reviewed thresholds;
- PostgreSQL + managed source + accepted evidence backup/clean restore and post-restore API verification;
- evidence schemas, transferred-evidence verification and final closure assessment;
- fail-closed release promotion bound to exact candidate source and intended verified-manifest SHA-256;
- repository verification and connected Task-17 validation workflow.

Current acceptance profile deliberately remains non-qualifying until approved quality/performance thresholds are supplied.

## 2. End-to-end architecture

The canonical product path is:

Camera → managed MP4 import → queue → leased worker → RTMDet → class mapping → class-separated ByteTrack → Task-9 result → attempt-scoped staging/publication → authoritative completion → Track search/detail → Evidence Review.

The acceptance harness observes this path only through public APIs. PostgreSQL/storage inspection is reserved for dedicated backup tooling and deterministic integration tests, not the product acceptance harness.

Candidate and production semantics remain distinct: candidate runs may have platformLockSha256=null; candidate bundle/selected-lock hashes are independently retained. Production runs require verified release/lock provenance.

## 3. Data provenance and integrity

Evidence binds:

- exact source commit;
- intended target verified-manifest SHA-256;
- model manifest, checkpoint, resolved config, pipeline profile, runtime profile and qualification hashes;
- selected bundle/lock identities;
- exact VideoAsset SHA-256 and strong ETag;
- exact ProcessingRun ID;
- exact accepted Track IDs;
- representative Artifact ID and bytes/ETag;
- corpus and individual ground-truth manifest SHA-256 values;
- exact host/device/runtime provenance.

Release promotion schema-validates gate-specific evidence; generic passing JSON cannot promote a gate.

## 4. Platform qualification

All four variants remain mandatory:

- windows-x86_64-cpu;
- windows-x86_64-cuda;
- linux-x86_64-cpu;
- linux-x86_64-cuda.

Qualification tooling compares the complete frozen hostCompatibility object encoded by the bundle, exact CPython patch identity, actual device, strict offline installation, pip check, real local RTMDet inference and full worker-flow evidence. CPU cannot substitute for CUDA and CUDA→CPU fallback fails closed.

Actual CUDA/offline evidence is not generated by hosted CI and remains pending until executed on the required hosts.

## 5. Quality acceptance

The evaluator uses normalized spatial boxes, bounded interpolation, temporal IoU, spatial IoU and polynomial min-cost maximum-flow matching with objective order:

1. maximum match cardinality;
2. total fixed-precision spatial IoU;
3. total fixed-precision temporal IoU;
4. deterministic lexical pair tie-break.

Formal qualification requires nonzero Person and Vehicle coverage plus explicit per-class precision/recall/F1 thresholds. Current profile is baseline/pending by design; no threshold values were invented.

## 6. Failure, security and recovery

Implemented coverage includes:

- stale worker authority cannot publish after failed/requeued processing;
- missing runtime provenance fails rather than completing;
- malformed persisted provenance causes attestation integrity failure;
- source/evidence hashes and ETags fail closed;
- bundle/path traversal and artifact-set integrity checks;
- outbound Internet reachability check in disconnected variant qualification;
- strict no-index/hash-only package install;
- fresh install cannot reuse a populated deployment destination;
- update requires an explicitly supported prior release and applicable migration policy;
- backup tooling rejects source symlinks, overlapping/nested roots and byte drift;
- clean restore revalidates Camera/Video/Run/Track/Artifact identity and media/evidence bytes through public APIs;
- promotion cannot bypass missing runtime/platform/quality/performance evidence.

## 7. Release truth and stopping rule

Before real-world evidence exists, tools/phase1/assess_phase1_closure.py must report implementation-complete-evidence-pending.

release-verified is permissible only after:

- runtime profile is fully qualified;
- all four runtime locks are qualified;
- every mandatory qualification gate is passed with validated evidence;
- fresh application install passes;
- supported offline update passes;
- backup/restore passes;
- formal CCTV quality passes;
- Linux NVIDIA recovery/performance passes;
- canonical release promotion succeeds;
- final production bundles and disconnected production-topology acceptance pass.
